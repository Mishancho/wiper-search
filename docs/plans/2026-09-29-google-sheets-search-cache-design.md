# Быстрый поиск дворников и тормозных колодок с Google Sheets

Дата: 2026-09-29

## Цель

Убрать обращение к Google Sheets из каждого поискового запроса по дворникам и тормозным колодкам, сохранив Google-таблицу единственным местом, где владелец просматривает и редактирует позиции. Новые данные любой из этих категорий могут появляться в поиске с задержкой до 1–5 минут.

Ускорение применяется ко всей поисковой базе. Ни один лист или тип детали нельзя исключать из кеша только потому, что его название или структура отличаются от листов с дворниками.

## Текущее состояние

`POST /search` при каждом запросе:

1. заново разбирает ключ service account;
2. создаёт клиент Google API;
3. открывает таблицу;
4. получает список всех листов;
5. скачивает все строки каждого листа;
6. нормализует все пары артикулов;
7. линейно перебирает полученный массив.

Поэтому основная задержка возникает до самого поиска. Бесплатный Render в данном случае не засыпает благодаря внешнему uptime-мониторингу, поэтому перенос на VPS не является обязательным условием ускорения.

## Принятое решение

Добавить внутри Flask-приложения кеш снимка Google Sheets и заранее построенный поисковый индекс. Обновлять снимок раз в 180 секунд в фоне. Не добавлять PostgreSQL, Redis или другой внешний datastore на первом этапе.

Google Sheets остаётся единственным источником истины:

```text
Google Sheets
    |
    | фоновая синхронизация раз в 180 секунд
    v
нормализованный неизменяемый снимок + поисковый индекс в памяти
    |
    | локальный lookup без сетевых запросов
    v
POST /search
```

## Компоненты

### Загрузчик Google Sheets

Загрузчик отвечает только за получение и разбор строк всех листов, используемых текущим поиском. В кеш обязательно входят дворники и тормозные колодки. Перед рефакторингом нужно зафиксировать фактические форматы строк обеих категорий, после чего выделить для них явные адаптеры. Ускорение не должно менять текущие результаты поиска или терять позиции из-за названия листа, секции либо категории.

Каждая нормализованная запись сохраняет категорию и секцию исходной строки. Если категория определяется названием листа или заголовком внутри листа, это правило оформляется явно и покрывается тестом, а не остаётся неявной проверкой только ключевых слов `front wipers` и `back wipers`.

Параметры подключения читаются при инициализации. Клиент Google API можно создавать для каждой фоновой синхронизации: при интервале в три минуты это не влияет на поиск и упрощает восстановление после сетевых ошибок.

### Построитель индекса

Сначала данные группируются по основному артикулу. Для каждой группы формируется окончательный ответ с полным набором артикулов и секцией. Затем каждый нормализованный артикул группы становится ключом индекса.

```text
нормализованный артикул -> список подходящих групп ответа
```

Нормализация запроса остаётся совместимой с текущим поведением: удаление пробелов по краям и перевод в верхний регистр. Один артикул может входить в несколько групп, поэтому значением является список, а не одна запись.

Индекс строится целиком вне общей ссылки. После успешной проверки готовый неизменяемый снимок одной операцией заменяет предыдущий. Поиск никогда не должен видеть наполовину обновлённые данные.

### Сервис кеша

Сервис кеша хранит:

- активный поисковый индекс;
- число исходных и нормализованных записей;
- время последней успешной синхронизации;
- время последней попытки;
- описание последней ошибки без секретных данных;
- признак готовности.

Один фоновый поток сразу выполняет первую загрузку, затем повторяет её каждые 180 секунд. Интервал задаётся переменной `SHEETS_REFRESH_SECONDS`, значение по умолчанию — `180`.

Для текущей небольшой нагрузки рекомендуется один Gunicorn worker с несколькими потоками. Это оставляет в процессе одну копию индекса и исключает дублирующие обращения к Google. Если в будущем понадобятся несколько процессов или экземпляров приложения, тогда потребуется общий внешний кеш либо отдельная синхронизация снимка.

### Поисковый endpoint

`POST /search` для дворников и тормозных колодок выполняет только:

1. проверку JSON и `part_number`;
2. нормализацию артикула;
3. чтение готового значения из активного индекса;
4. возврат существующего формата ответа.

Endpoint не обращается к Google Sheets, не нормализует весь набор данных и не сканирует его целиком.

### Диагностика

`GET /health` остаётся лёгким liveness-endpoint для uptime-мониторинга: он отвечает, не ожидая Google Sheets. Первое входящее обращение, в том числе uptime-проверка, запускает фоновую синхронизацию один раз. В ответ добавляются безопасные поля `cache_ready`, `last_success_at`, `record_count` и `refresh_error`.

До первой успешной загрузки `/search` возвращает `503` с понятным сообщением о подготовке базы. После первой загрузки временная недоступность Google не влияет на поиск.

## Обработка ошибок

- Ошибка Google API записывается в состояние кеша и журнал без содержимого service-account ключа.
- После хотя бы одной успешной загрузки любая ошибка обновления оставляет предыдущий снимок активным.
- Пустой результат не заменяет непустой активный снимок: он считается подозрительной загрузкой и фиксируется как ошибка.
- Одновременно выполняется не более одной синхронизации.
- Неожиданная строка в одном листе не должна разрушать уже собранные корректные строки других листов или категорий.
- Ошибка разбора листа с одной категорией не должна удалять последнюю рабочую копию другой категории.
- Если первая загрузка ещё не завершилась или ни разу не удалась, поиск отвечает `503`, а не сообщает, что артикул не найден.

## Развёртывание

Первый релиз остаётся на Render. Рекомендуемая конфигурация Gunicorn: один worker и несколько потоков. Uptime-монитор продолжает обращаться к `/health`.

Перенос на арендованный VPS является отдельной операцией после проверки кеша. Он даст больше контроля и позволит позже хранить резервный JSON-снимок на диске, но не требуется для устранения текущей задержки.

## План реализации

### Шаг 1. Зафиксировать текущее поведение поиска

- Зафиксировать по несколько обезличенных строк из фактических листов дворников и тормозных колодок, включая их заголовки и способ определения категории.
- Добавить тестовые данные обеих категорий с несколькими основными артикулами, общим альтернативным артикулом, разным регистром и секциями.
- Зафиксировать текущий JSON-контракт `/search` и поведение для пустого и отсутствующего артикула.
- Убедиться, что оптимизация не меняет состав и сортировку выдачи.

### Шаг 2. Выделить загрузку и построение индекса

- Отделить чтение Google Sheets от Flask endpoint.
- Реализовать чистую функцию построения единого поискового индекса для дворников и тормозных колодок.
- Выделить явный разбор фактического формата каждой категории и сохранить текущее поисковое поведение без продуктовых изменений.
- Добавить тесты группировки, категории, секции, нормализации и поиска по основному и альтернативному артикулам для обоих типов деталей.

### Шаг 3. Добавить потокобезопасный кеш

- Реализовать состояние снимка и атомарную замену индекса.
- Добавить фоновую первичную загрузку и обновление по интервалу.
- Не допускать параллельных refresh-операций.
- При ошибке сохранять последнюю успешную копию.
- Сделать интервал настраиваемым через `SHEETS_REFRESH_SECONDS`.

### Шаг 4. Переключить `/search` на индекс

- Удалить загрузку Google Sheets из пути обработки запроса.
- Выполнять lookup по нормализованному ключу.
- Сохранить существующие HTTP-коды и формат успешных ответов.
- Добавить отдельный `503` для ещё не готового кеша.

### Шаг 5. Добавить наблюдаемость

- Расширить `/health` метаданными кеша без секретов.
- Логировать начало, успешное завершение, длительность и ошибки синхронизации.
- Проверить, что health-check отвечает, не ожидая Google Sheets.

### Шаг 6. Настроить процесс приложения

- Установить один Gunicorn worker и несколько threads в `Procfile`.
- Описать `SHEETS_REFRESH_SECONDS` в `env.example` и README.
- Сверить документацию по service-account ключу с фактическим способом чтения переменных окружения.

### Шаг 7. Проверить и выпустить на Render

- Запустить все локальные тесты.
- Проверить, что серия поисков вызывает Google Sheets только во время refresh, а не на каждый запрос.
- Измерить несколько последовательных запросов к `/search` до и после изменения.
- После деплоя проверить `/health`, известный артикул, неизвестный артикул и появление новой строки из Google Sheets не позднее чем через пять минут.
- Оставить перенос на VPS отдельным решением после подтверждения результата.

## Проверки

Планируется использовать стандартный `unittest`, чтобы не добавлять runtime-зависимости:

```bash
python -m unittest discover -s tests -v
```

Обязательные сценарии:

1. повторные поиски не вызывают загрузчик Google Sheets;
2. поиск по основному и альтернативному артикулу дворника возвращает прежний контракт;
3. поиск по основному и альтернативному артикулу тормозной колодки возвращает прежний контракт;
4. регистр и внешние пробелы не влияют на результат;
5. один артикул может вернуть несколько групп;
6. в одном снимке одновременно доступны обе категории;
7. успешный refresh атомарно публикует новый индекс;
8. ошибка refresh сохраняет старый индекс;
9. пустая загрузка не уничтожает рабочий снимок;
10. до первой успешной загрузки поиск возвращает `503`;
11. health-check отвечает, не ожидая сетевой синхронизации;
12. два одновременных refresh не выполняются параллельно.

## Критерии готовности

- В обработчике `/search` нет обращений к Google Sheets ни для дворников, ни для тормозных колодок.
- После прогрева поиск использует один lookup по индексу вместо полного прохода по данным.
- Дворники и тормозные колодки находятся через один быстрый индекс и возвращают совместимый с текущим frontend ответ.
- Изменение любой из двух категорий в Google Sheets появляется в поиске не позднее пяти минут при исправной синхронизации.
- Кратковременная ошибка Google не прерывает поиск по последней успешной копии.
- Формат существующих успешных ответов остаётся совместимым с frontend.
- На Render подтверждено, что повторные запросы отвечают без текущей многосекундной задержки.

## Отложено

- PostgreSQL, Redis и иные внешние базы.
- Перенос на VPS.
- Резервный снимок на постоянном диске VPS.
- Ручной административный endpoint обновления.
- Продуктовое изменение структуры листов, правил аналогов или формата выдачи. При этом поддержка и ускорение уже существующего поиска тормозных колодок входят в текущую задачу обязательно.
